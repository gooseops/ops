# Book a Call Pipeline, Supporting Infrastructure Work, and a Documentation Cleanup Pass

## Overview

This was a long, multi-day session spanning infrastructure work, live debugging, and a final documentation audit. The headline outcome is that the maintainer's website now has a fully working "book a call" button, backed by two new Ansible roles working together with an existing Nextcloud calendar deployment. Along the way, several other services got built or hardened, a WireGuard identity got issued, a set of homelab services got formally decommissioned, and the session closed with a full repository once-over to catch stale comments and documentation before wrapping up.

## Why This Exists

The maintainer runs GooseOps as a solo consulting practice, and the public website needed a real scheduling flow so visitors could book a call directly rather than exchanging emails. That single business need drove most of this session: a booking application had to go up, it needed to know the maintainer's real calendar availability to avoid double-booking, and both pieces needed to be deployed as proper Ansible roles rather than one-off manual setup, consistent with how every other service in this repository is managed.

Several supporting initiatives were also either finished or meaningfully advanced this session: a Kubernetes-adjacent virtualization platform called Incus got its Terraform module and Ansible role support ported over as generic, reusable building blocks; a business management suite called Odoo got deployed with a tricky PDF-rendering dependency finally resolved; a video conferencing service called Jitsi Meet and its companion relay server, coturn, got meaningfully hardened around network traversal and meeting authentication; and a backup role using the Restic engine got built out with real job scheduling. None of these were the headline goal, but they represent real progress recorded here so future sessions have accurate context.

## Technical Decisions

The booking application chosen was Easy!Appointments, deployed as a Docker Compose stack alongside a bundled MariaDB database — the first role in this repository needing MySQL-family storage rather than the shared Postgres host every other database-backed role points at. That was a deliberate scope decision: no shared MySQL role exists yet, so bundling was simpler than building shared infrastructure for a single consumer.

Getting the maintainer's actual Google Calendar availability into the booking flow required a second, new role built around a script the maintainer had already written: a one-way sync from Google Calendar into a Nextcloud calendar, authenticating as a Google service account with domain-wide delegation rather than a browser-based login, specifically so it could run unattended on a schedule. That role was deliberately kept separate from a generic "run any script on a schedule" abstraction — the reasoning was that a generic role would either have to reinvent the per-job credential-and-assertion discipline this repository already uses, or lose it, and a single script didn't justify the abstraction yet.

A meaningful mid-session decision was where that calendar-sync role should actually run. Three hosts were considered: the Nextcloud host itself, the new booking-application host, or a dedicated new host. The Nextcloud host won, because the sync script's only real dependency is the calendar it writes into — colocating there means a much shorter network path, and it deliberately avoids the one host with a public internet-facing address, since the sync script carries a genuinely sensitive credential.

On the Terraform side, a lengthy but ultimately unresolved discussion happened around switching the Proxmox virtual machine provider from the aging Telmate provider to the newer, actively maintained "bpg" provider. The finding worth remembering: the two providers use completely different resource shapes, and critically, the newer provider has no way to clone a virtual machine template by name — only by its numeric ID — while the maintainer's whole workflow currently depends on cloning by name. That's a real migration cost, not just a syntax change, and no decision was made to actually switch.

Late in the session, a batch of homelab services were intentionally decommissioned from the live inventory: the video conferencing stack, a real-time media server, a chat server, and a couple of smaller services. Their Ansible roles were deliberately kept in this repository as generic, reusable boilerplate rather than deleted, since this repository's whole purpose is to be a public portfolio of infrastructure patterns, not a mirror of exactly what one homelab currently runs.

## Dependencies

The booking application depends on a Google Cloud service account with domain-wide delegation authorized in the Google Workspace admin console — a manual, console-only setup step with no API to automate, confirmed by checking Google's own administrative API and finding it only supports listing and deleting existing app-specific credentials, never creating new ones. The same "no creation API" limitation applies to Google's account-level app passwords, used both for the booking application's outbound email and, separately, for authenticating to Nextcloud's calendar protocol.

The calendar-sync script depends on a small Python virtual environment with a handful of Google API client libraries and a calendar protocol library. A real, confusing bug surfaced here: running the virtual environment setup from inside this repository's pinned development shell let a completely different, incompatible copy of one of those libraries leak in ahead of the one actually installed, because of an inherited environment variable — the fix was rebuilding the virtual environment outside that development shell.

The booking application's container image ships without two things needed for a clean production deployment: a rewrite rule for clean URLs, and an Apache web server module to actually enable that rule. Both were checked against the actual container image's startup script before implementing a fix, confirming there was no simpler built-in mechanism — the fix layers two small configuration files onto the container as read-only mounts and enables the missing module at container startup, without needing to build a custom image.

## How It Fits Together

The full booking flow now works like this: the maintainer's real calendar commitments sync one-way from Google Calendar into a dedicated Nextcloud calendar, on a tight one-minute schedule chosen specifically to shrink the window where a newly added personal commitment could collide with someone booking that same slot publicly. The booking application then reads and writes into that same Nextcloud calendar through its own built-in two-way calendar sync, so a real booking blocks that slot from being offered again, and the maintainer's personal calendar events block bookings the other direction. Both roles are deployed through this repository's normal Ansible pattern — one playbook per service, secrets sourced through the secrets manager, never hardcoded — and both got genuinely deployed and exercised against real infrastructure this session, not just checked for syntax.

The booking application also picked up basic brand consistency with the maintainer's public website: a matching accent color, a dark visual theme, and — after some back and forth about the right way to do it — the website's actual favicon, fetched at deployment time from the live website rather than duplicated as a file inside this repository, since a business-specific icon doesn't belong committed into a public, reusable codebase.

## Gotchas

Several real bugs got caught by actually running things against live infrastructure rather than trusting a clean automated check. The calendar-sync script was missing a timestamp field required by the calendar standard it writes to, silently patched around by a client library rather than failing loudly — now fixed at the source. A Nextcloud quirk turned into a real time sink: deleting a calendar through its web interface does not actually free up its name for reuse, even after emptying the trash, and repeated attempts to reclaim the original name just kept consuming numbered variants. The eventual reliable fix was deleting via the command line with a flag that bypasses the trash entirely, done while the calendar was still active rather than after already deleting it.

The booking application was also initially pinned to an outdated version — a real research gap, not a deliberate choice, since a newer stable release had already shipped before this role was even built. That was caught by the maintainer directly rather than through any internal check.

Finally, a full repository documentation pass at the very end of the session caught several comments and a couple of README files that described homelab services in the present tense — as if they were still actively running — when in fact they'd been decommissioned earlier in the same session. One of those stale comments also named a real, specific internal domain name that had no reason to be sitting in this public repository. All of these were rewritten to describe the underlying patterns generically rather than as claims about currently-running infrastructure, plus a couple of small unrelated stale comments and one documentation typo found along the way.

## What's Next

The immediate next step is pairing the booking application with the Nextcloud calendar through its own calendar-sync settings, and then running one real booking all the way through: the public booking page, the confirmation email, and confirming the slot actually becomes unavailable afterward. Beyond that, a handful of longer-running items remain open: confirming the cloud proxy's billing account is genuinely active rather than just assumed to be, finishing a live-hosts validation pass on several roles that have only been checked for syntax so far, resolving a hardware blocker on the virtualization migration, and a still-pending cleanup of a personal scratch notes file that duplicates content now properly documented elsewhere.
